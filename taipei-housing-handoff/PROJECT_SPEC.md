# 台北房屋觀察簿 — Rust 後端 + Web 前端 改寫規格

## 背景

這個專案原本用「跟 Claude.ai 對話 + claude-in-chrome 瀏覽器擴充功能」手動維運：
每次要更新，都要請 Claude 打開瀏覽器抓 591 搜尋結果、跟舊資料比對、判斷新物件/下架/重複刊登、
更新 JSON、重建互動網頁（Claude Artifact）、使用者再手動複製新網址、JSON 手動下載上傳回 Project。

這次要重寫成一個獨立服務：**Rust 後端 + Web 前端**，自己排程抓取、自己存資料庫、
不再需要人在中間手動搬運檔案或複製網址。

`data/` 資料夾裡的 8 個 JSON 檔案是目前累積的完整歷史資料（含去重、下架、代表轉移紀錄），
**必須先寫 migration 腳本把這些匯入新資料庫，不能捨棄**——裡面有大量手動判斷過的去重結果。

## 資料結構（沿用現有JSON schema，作為資料庫設計依據）

每份追蹤清單對應資料庫裡的一組紀錄，欄位：

```jsonc
{
  "searchUrl": "...",       // 591原始搜尋網址
  "artifactUrl": "...",     // 舊系統的Claude Artifact連結，新系統可廢棄或改成前端網址
  "criteria": {...},        // 區域/類型/價格區間描述
  "lastChecked": "2026-08-31",
  "history": [               // 每次檢查的紀錄
    {
      "date": "2026-08-31",
      "newCount": 2,
      "totalCount": 117,
      "newIds": ["20819248", "20815651"],
      "delistedIds": ["20565563", "20633715"],
      "note": "..."          // 人類可讀的當次異動說明
    }
  ],
  "listings": [               // 所有曾出現過的物件（含重複刊登）
    {
      "id": "20819248",           // 591物件id
      "title": "...",
      "price": 3480,               // 萬元
      "unitPrice": 95.87,          // 萬/坪
      "rooms": "3房2廳2衛",
      "area": "36.3",               // 權狀坪數
      "mainArea": "26.09",          // 主建坪數，可能為null
      "age": 37,                    // 屋齡，可能為null
      "floor": "15F/20F",
      "community": "建成花園廣場",   // 社區/大樓名稱，可能為null
      "address": "松山區-民生東路五段",
      "agent": "仲介張芯菲",
      "firstSeen": "2026-08-31",
      "duplicateOf": "20742570",    // null=代表刊登；非null=重複刊登，指向代表刊登id
      "delisted": true,              // 可選，真下架時才有
      "delistedDate": "2026-08-31"   // 可選
    }
  ]
}
```

**代表刊登（`duplicateOf: null`）才會顯示在前端頁面上**，重複刊登只留存在資料庫裡避免重複通知。

## 核心業務邏輯（從實際運作中歸納出的規則，務必保留）

### 1. 抓取層
- 591 是 JS 渲染的 SPA，純 HTTP 抓取拿不到列表內容。建議：
  - **優先方案**：用瀏覽器開發者工具的 Network 分頁，找出 591 前端呼叫的底層 JSON API，直接呼叫該 API（不需要真的渲染頁面，速度快很多）
  - **備用方案**：headless browser（`headless_chrome` crate 或透過 WebDriver 的 `fantoccini`）模擬瀏覽器抓取
- 列表卡片的 CSS class 是 `.ware-item`；分頁用 `.paginator-container`，數字按鈕需要用點擊模擬（不能直接用 `firstRow=N` 改網址參數跳頁，591 不會正確重新載入內容）
- 591 近期（2026-08前後）在搜尋結果中混入越來越多「熱銷建案」預售屋卡片與「猜你喜歡」推薦區塊，這些跟 `.ware-item` 的 class 不同或內容格式不同，抓取時務必過濾掉，只留真正符合篩選條件的中古屋卡片
- 591 頁面上偶爾會出現「24開頭」id 的追蹤/重導連結，每次抓取id都會變、內容其實對應頁面上其他既有物件，**不是真實新刊登**，比對時應以標題/仲介/價格/坪數/樓層等內容欄位判斷是否為已知物件的追蹤連結，符合的話捨棄不列入資料庫

### 2. 去重邏輯（同一戶被不同仲介重複刊登，非常常見，尤其電梯大樓類）
判斷兩筆刊登是否為同一戶的依據（按優先順序）：
- 基本比對：`community`/`address` + `floor` + `area` 是否吻合
- `area` 允許 0.1 坪內誤差（不同仲介登打常有微小差異）
- 降價前後兩筆刊登視為同一戶：**價格不同不代表不是同一戶**
- `community` 欄位文字不同、但 `address`/`floor`/`area`/`mainArea` 都吻合 → 視為同一戶（同一棟樓有時被登記成不同社區名）
- 樓層標示格式不一致但實際是同一複層/樓中樓單位（如 `1F~2F/8F` vs `1F/8F`）→ 視為同一戶，用 `mainArea` + `age` 完全一致來確認
- `mainArea` + `age` 完全相同是很強的同戶訊號，社區名或地址寫法不一致時特別有用

實測案例：松山區-電梯大樓-4000 這組 108 筆原始物件裡只有 23 筆是真正不同戶（重複率約79%），
單一戶最多曾被 13 家不同仲介重複刊登過。

### 3. 下架偵測（每次檢查都要做）
把當次抓到的所有物件 id（不分代表/重複）整理成集合，跟資料庫裡「`duplicateOf` 為 null 且尚未標記 delisted」的每筆代表物件比對：

- **真下架**：代表物件本身 + 該戶所有已知重複刊登 id 全部從抓取結果中消失 → 標記 `delisted: true`, `delistedDate`。**該筆物件仍保留在資料庫、仍顯示在前端頁面上（帶下架徽章），不可移除或隱藏**
- **代表刊登轉移**（重要例外）：代表物件本身消失，但該戶「曾被判定重複」的其他仲介刊登仍在抓取結果中 → **不算下架**，而是把代表刊登轉移給現存的那筆（通常選現存 id 中數字最小的一筆），更新兩者的 `duplicateOf`
- **重新上架**：先前標記 `delisted` 的物件，若其 id 或內容完全相同的新 id（同標題同仲介同規格）重新出現在抓取結果中 → 移除 `delisted`/`delistedDate`，若是換了新 id，則代表刊登也要轉移到新 id 上，同時保留原本的評價/歷史紀錄
- 每次的 `history` 要記錄當次的 `newIds`、`delistedIds`，並寫一段人類可讀的 `note`

### 4. 使用者評價
- 每筆代表物件對應「要 / 不要 / 原因」評價，需要跨裝置同步、持久化
- 新系統直接存進資料庫（用 `591_id` 當 key），不再需要像舊系統那樣依賴 Claude Artifact 的 storage API，也不再有「重新整份發布會遺失使用者評價，需要人工截圖合併」的痛點——這是新架構相對舊流程最大的改善

### 5. 通知
- 每次排程檢查後，若有新物件或下架，應該要推播/寄信通知使用者（這是舊系統文件裡本來就設計好、但從未真正落地的功能）

## 建議技術棧

**後端（Rust）**
- Web框架：`axum` 或 `actix-web`
- 資料庫：SQLite（`sqlx` 或 `rusqlite`），單機/小VPS足夠
- 排程：`tokio-cron-scheduler`，建議每天固定時間（例如台北時間08:00）自動跑8組抓取
- 抓取：優先研究591底層API直連（用瀏覽器開發者工具的Network分頁找），退而求其次用 `fantoccini`（WebDriver）或 `headless_chrome`
- 通知：`lettre`（Email）

**前端（Web）**
- 簡單 SPA（React/Vue/Svelte）或 Rust 伺服器端渲染（`askama` 模板 + `htmx`）
- 畫面沿用現有設計：卡片式列表、要/不要按鈕＋原因輸入框、下架徽章（淡化+刪除線）、代表轉移小提示、統計列（追蹤中/今日新增/已評價/要的/已下架）
- 標題可點擊連回 591 原始物件頁面（`https://sale.591.com.tw/home/house/detail/2/{id}.html`）

## 待辦優先順序建議

1. 設計 SQLite schema（對應上面的資料結構），寫 migration 腳本匯入 `data/` 裡的 8 個 JSON
2. 研究 591 前端呼叫的底層 API（開發者工具 Network 分頁），評估是否可行；不行的話用 headless browser
3. 實作單一組（例如中山華廈-3000）的抓取＋去重＋下架判斷邏輯，跑通後複製成其他7組的設定
4. 排程器 + 前端頁面 + 評價寫入API
5. Email/推播通知

## 使用須知（591平台相關）

- 591 的服務條款可能限制自動化抓取行為，建議控制抓取頻率（一天一次即可），只抓公開頁面，避免造成該站負擔
- 591 頁面結構可能會變動（`.ware-item` 這類 CSS class name 未必永久有效），抓取層要寫得容易維護、方便日後調整選擇器
